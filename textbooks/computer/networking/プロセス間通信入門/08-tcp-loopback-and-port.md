# 8. TCP ループバックとポート

## 8.1 TCP ループバック

TCP ループバックは、自分自身のマシンに向けた TCP 通信である。宛先に `127.0.0.1`（IPv6 では `::1`、名前では `localhost`）を指定すると、パケットは外に出ずに同じマシンの中で折り返す。

- **仕組み**：OS には、ループバックインターフェースという仮想のネットワークカードがある（Linux は `lo`、macOS は `lo0`）。ここに送ったパケットは、物理的なネットワークカードにもケーブルにも出ず、カーネルの中でそのまま受信側に戻る。
- **アドレス**：`127.0.0.0/8` の範囲全体がループバック用である。普通は `127.0.0.1` を使う。
- **Unix ソケットとの違い**：外には出ないが、TCP/IP の処理はすべて通る（ヘッダの付与、チェックサム、ACK、ハンドシェイクなど）。この分だけ Unix ソケットより遅い（[6章](06-performance.md)の測定では約 15 µs の差）。
- **よく使われる理由**：普通の TCP と同じ書き方で済むので、ネットワーク越しに使う予定のプログラムを手元でそのまま試せる。`localhost:3000` で開発サーバーを動かすのが典型例である。

ループバックインターフェースは `ifconfig lo0`（macOS）や `ip addr show lo`（Linux）で確認できる。

## 8.2 レイヤーごとのポートの位置づけ

| レイヤー | 宛先を表すもの | ポートの扱い |
|---|---|---|
| L2 Ethernet | MAC アドレス（どの機器か） | 存在しない |
| L3 IP | IP アドレス（どのマシンか） | 存在しない。IP ヘッダには、次に渡す先が TCP（6）か UDP（17）かを示す番号だけがある |
| L4 TCP / UDP | ポート番号（マシンの中のどのソケットか） | ここで初めて登場する。ヘッダに送信元ポートと宛先ポートが2バイトずつある |
| L7 アプリ | URL など | 80 は HTTP、5432 は PostgreSQL、といった番号は慣習であって、仕組みとしての意味はない |

## 8.3 ポートの実体

ポートの実体は次の2つで、それ以上のものはない。

1. **パケットの中**：TCP ヘッダの先頭4バイトが、送信元ポートと宛先ポート（各16ビット）である。
2. **カーネルの中**：ソケットを探すためのテーブルのキーである。受信で引くテーブルは2種類ある（詳しくは[9章](09-listening-table.md)、テーブルの一覧は[13章](13-tables-overview.md)）。
   - 待ち受けソケットテーブル：`(IP, ポート) → 待ち受けソケット`
   - 確立済み接続テーブル：`(送信元 IP, 送信元ポート, 宛先 IP, 宛先ポート) → 接続済みソケット`

## 8.4 ポートに関わる処理

- **`bind()` と `listen()`**：`bind()` でカーネルがそのポートが空いているか確認し、空いていれば予約する。使用中なら `Address already in use` になる。続く `listen()` で待ち受けソケットテーブルに登録され、接続を受け付けられるようになる（[9章](09-listening-table.md)）。
- **受信**：IP 層が「宛先 IP は自分か」を確認する。次に TCP 層がヘッダから宛先ポートを読み、テーブルを引いてソケットを見つける。データはそのソケットの受信バッファに入り、待っているプロセスが起こされる。
- **送信**：カーネルが、ソケットに記録されているポート番号をヘッダに書き込む。
- **クライアント側**：`connect()` するときに、カーネルが送信元ポートを自動で割り当てる（エフェメラルポート）。検証に使った Mac では、`sysctl` で確認した範囲が 49152〜65535 だった。

## 8.5 ポートと fd は別物

どちらもソケットを指す番号だが、誰のための番号かが違う。

| | fd | ポート |
|---|---|---|
| 誰が使うか | プロセス（自分のソケットを指す） | 外から来たパケット（宛先のソケットを探す） |
| 有効な範囲 | そのプロセスの中だけ。プロセス A の fd 3 とプロセス B の fd 3 は別物 | マシン全体（IP アドレスごと） |
| 実体 | プロセスごとの fd テーブルの添字 | ソケットに記録された番号。カーネルのテーブルを引くときのキー |
| 番号の決まり方 | 空いている一番小さい番号（0, 1, 2 の次は 3） | `bind()` で指定するか、カーネルが自動で割り当てる |

```
プロセス --fd--> [ソケット（カーネル内）] <--ポート-- 外から来たパケット
```

ソケットが真ん中にあり、プロセスの側からは fd で、ネットワークの側からはポートでたどり着く。ポートはプロセスではなくソケットに結びついている。

1対1にならない例もある。

- **1つのポートに多くの fd**：Web サーバーが 80 番で `accept()` すると、接続ごとに新しい fd が返る。どの接続済みソケットも、自分の側のポートは 80 のままである（区別できる理由は 8.7）。
- **1つのソケットに複数の fd**：`fork()` すると、親プロセスと子プロセスがそれぞれの fd で同じソケットを指す（実例は[9章](09-listening-table.md)）。
- **ポートのないソケット**：Unix ソケットにはポートがない。fd はあり、名前はファイルパスで表す。

## 8.6 ポートは Unix ソケットのファイルパスにあたる

ポートは Unix ソケットとは関係ないが、役割は似ている。

| | 待ち受けアドレス |
|---|---|
| Unix ソケットのサーバー | ファイルパス（例：`/var/run/docker.sock`） |
| TCP ソケットのサーバー | IP アドレス + ポート（例：`127.0.0.1:8080`） |

ポートは、Unix ソケットでのファイルパスにあたるものを TCP で表したものである。ただし、ポート番号だけでは待ち受けアドレスにならず、IP アドレスと組み合わせて初めて完全なアドレスになる。また、ポートはサーバー専用ではなく、クライアント側のソケットにも送信元ポート（エフェメラルポート）が必ず割り当てられる。

## 8.7 4つの組で接続を区別する

同じポートで複数の接続を区別できるのは、接続がポート1つではなく、次の4つの値の組で区別されるからである。

```
(送信元 IP, 送信元ポート, 宛先 IP, 宛先ポート)
```

例えば、サーバーの 80 番ポートに3つの接続があるとする。

| 送信元 IP | 送信元ポート | 宛先 IP | 宛先ポート |
|---|---|---|---|
| 10.0.0.5 | 51000 | 10.0.0.1 | 80 |
| 10.0.0.5 | 51001 | 10.0.0.1 | 80 |
| 10.0.0.9 | 51000 | 10.0.0.1 | 80 |

宛先ポートはどれも 80 だが、4つの組で見るとすべて違う。1行目と2行目は同じクライアントからの接続だが、送信元ポートが違う。1行目と3行目は送信元ポートが同じだが、送信元 IP が違う。

パケットを受け取ったとき、カーネルは次の順でテーブルを引く。

1. 4つの組で確立済み接続テーブルを探す。見つかれば、その接続済みソケットに渡す。
2. 見つからず、それが新しい接続要求（SYN）であれば、`(宛先 IP, 宛先ポート)` で待ち受けソケットテーブルを探し、待ち受けソケットに渡す。

逆に言うと、4つの組が同じ接続は同時に作れない。そのため、1つのクライアント IP から同じサーバーの同じポートへ同時に張れる接続の数は、エフェメラルポートの数が上限になる。範囲が 49152〜65535 なら約1.6万本である。
