# 9. カーネルの待ち受けソケットテーブル

## 9.1 抽象：辞書として見る

待ち受けソケットテーブルは、抽象的には `(プロトコル, 自分の IP, ポート) → 待ち受けソケット` という辞書である。`netstat -an -p tcp | grep LISTEN`（macOS）を実行すると、このテーブルの中身がほぼそのまま見える。整理すると次のようになる。

| キー（プロトコル, IP, ポート） | 値 |
|---|---|
| (TCP, 0.0.0.0, 80) | nginx の待ち受けソケット |
| (TCP, 0.0.0.0, 8082) | 何かのサーバーの待ち受けソケット |
| (TCP, 127.0.0.1, 5432) | 例：ローカル専用の PostgreSQL |

パケットが届いたときの引き方は、次の擬似コードのようになる。

```
lookup(宛先IP, 宛先ポート):
    完全一致 (宛先IP, ポート) があれば → それを返す
    なければワイルドカード (0.0.0.0, ポート) があれば → それを返す
    どちらもなければ → 見つからない（カーネルが RST を返す。ポートスキャンでいう closed）
```

例えば、外から `10.0.0.1:5432` 宛ての SYN が届いても、テーブルには `127.0.0.1` の登録しかないので一致せず、closed になる。これが「`127.0.0.1` で待ち受けると外から見えない」理由である（[10章](10-port-scan.md)）。

## 9.2 実体：カーネルのメモリ上のハッシュ表（Linux の例）

```
listening_hash[ハッシュ(ポート, IP) % バケット数]
   ├─ バケット 0: → sock A → sock B   （連結リスト）
   ├─ バケット 1: (空)
   └─ バケット 2: → sock C
```

- 配列の各要素（バケット）に、ソケットの構造体（`struct sock`）が連結リストでつながっている。ポートと IP からハッシュ値を計算してバケットを選び、リストをたどってキーが一致するものを探す。
- `bind()` でポート使用状況テーブル（`bhash`）に記録され、`listen()` で待ち受けソケットテーブルに追加される。`close()` で両方から削除される。
- Linux のソースでは、`inet_hashinfo` という構造体の中に役割の違うテーブルが並んでいる。待ち受けソケットテーブル（`lhash2`）、確立済み接続テーブル（4つの組がキー、`ehash`）、ポート使用状況テーブル（`bhash`。`Address already in use` の判定に使う）である。テーブルの一覧は[13章](13-tables-overview.md)にまとめた。
- macOS は BSD 系のカーネルで、名前が違う（`inpcb` という構造体をハッシュ表で管理する）。考え方は同じである。

構造体の名前は記憶にもとづく。正確には Linux のソースの `include/net/inet_hashtables.h` で確認すること。

## 9.3 実例：ポート 80 で待ち受ける nginx

macOS で nginx が 80 番を使っているときの `lsof` の出力である。

```
$ lsof -nP -iTCP:80 -sTCP:LISTEN
COMMAND  PID   USER   FD   TYPE  DEVICE              NAME
nginx   2323   ...    7u   IPv4  0x84c73cb2c8d2294d  TCP *:80 (LISTEN)
nginx   2597   ...    7u   IPv4  0x84c73cb2c8d2294d  TCP *:80 (LISTEN)
```

- 2つの nginx プロセスが、それぞれ fd 7 を持っている。
- `DEVICE` 列の値（カーネル内のソケットのアドレス）が同じなので、2つの fd は同じ1つの待ち受けソケットを指している。`fork()` で1つのソケットを複数の fd が指す例である（[8章](08-tcp-loopback-and-port.md)）。
- `*:80` は `0.0.0.0:80` のことで、すべてのインターフェースで待ち受けている。外からのスキャンでも見える。

## 9.4 プロセスの中で起きていること

```c
fd = socket(AF_INET, SOCK_STREAM, 0);  // カーネルにソケットを作る。プロセスは fd（この例では 7）を受け取る
bind(fd, 0.0.0.0:80);                   // 80 番を予約する（ポート使用状況テーブルに記録）
listen(fd, backlog);                    // 待ち受けソケットテーブルに登録する
for (;;) {
    c = accept(fd);           // 接続が来るまで眠る。来たら新しい fd が返る
    read(c, buf);             // リクエストのバイト列を、自分のメモリの buf にコピーしてもらう
    /* HTTP を解析してレスポンスを作る（ここだけがプロセス自身の処理） */
    write(c, resp);           // レスポンスをカーネルにコピーしてもらう
    close(c);                 // keep-alive なら閉じずに次の read へ進む
}
```

（`bind` の引数は説明のために簡略化している。実際は `struct sockaddr_in` にアドレスとポートを入れて渡す。）

ポートそのものはカーネルのテーブルにある。プロセスのメモリにあるのは、fd の番号と、読み書きに使うバッファだけである。nginx は実際にはこのループを1つずつ回すのではなく、`epoll`（macOS では `kqueue`）で多くの fd をまとめて見張っている。

## 9.5 1024 未満のポート

1024 未満のポートは、伝統的には root だけが使える特権ポートとされている。Linux では root か `CAP_NET_BIND_SERVICE` 権限が必要である。

macOS では事情が違う。検証に使った Mac では、一般ユーザー（uid 501）でも 81 番を `0.0.0.0` で bind できた。nginx が一般ユーザーで 80 番を使えるのも、この macOS の挙動による。
