# 6. 性能

## 6.1 アドレスの番号の遠さは関係ない

接続済みソケットのペアのメモリアドレスが離れていても、速度にはほぼ影響しない。RAM はどの番地でも同じ速さで読み書きできるランダムアクセスのメモリであり、プログラムが見るアドレスも仮想アドレスなので、番号の近さは物理的な近さと一致しない。

## 6.2 速度が変わる条件

| 条件 | 内容 |
|---|---|
| NUMA | 複数 CPU ソケットのサーバーでは、各 CPU に近いメモリと遠いメモリがある。送信側と受信側が別の CPU ソケットで動くと遅くなる。「メモリが遠い」が実際に起きるのはこれ |
| CPU キャッシュ | L2 や L3 キャッシュを共有するコア同士なら速く、離れたコアだとキャッシュ間の転送が増えて遅くなる |
| システムコールの回数 | 小さいデータを何度も送ると `write()` / `read()` のコストが積み重なる。まとめて送るほうが速い |
| バッファの空き | 受信側の読み取りが遅いとバッファが埋まり、送信側の `write()` が待たされる |
| スケジューリング | 相手のプロセスが起きるまでのコンテキストスイッチの待ち時間 |

## 6.3 コピーをなくす

Unix ソケットではデータが2回コピーされる（[3章](03-kernel-and-process.md)）。大量のデータを最速で受け渡したい場合は、コピーをしない共有メモリ（[4章](04-shared-memory.md)）を使う。

## 6.4 Unix ソケット・TCP ループバック・HTTP/1.1 の遅延

「Unix ソケットと HTTP のどちらが速いか」は、そのままでは比べられない。HTTP は Unix ソケットの上でも動くからだ（Docker の API は `docker.sock` の上で HTTP を話している）。比べるときは、次の2つに分けて考える。

| 比較 | 差が出る理由 |
|---|---|
| 通り道：Unix ソケット vs TCP ループバック（[8章](08-tcp-loopback-and-port.md)） | TCP は IP と TCP の処理（ヘッダ、チェックサム、ACK、輻輳制御）、ハンドシェイク、TIME_WAIT を通る。Unix ソケットはどれも通らない |
| 話す中身：HTTP vs 生のバイト列 | HTTP はテキストのヘッダを作る処理と読み解く処理が毎回かかる。小さいメッセージほど、この割合が大きくなる |

macOS 上の Node v26 で測った結果を示す。1バイトを往復させたときの往復時間で、接続は使い回し（keep-alive）、2回測定した。

| 組み合わせ | p50 | p99 |
|---|---|---|
| Unix ソケット + 生のバイト列 | 6 µs | 14 µs |
| TCP ループバック + 生のバイト列 | 21 µs | 38〜40 µs |
| Unix ソケット + HTTP/1.1 | 26〜27 µs | 45〜68 µs |
| TCP ループバック + HTTP/1.1 | 43 µs | 105〜124 µs |

2回の測定で p50 はほぼ同じで、p99 は少しぶれた。

- **通り道の差**：TCP にすると約 15 µs 増える。生のバイト列では約3.5倍の差になる。
- **HTTP/1.1 の上乗せ**：どちらの通り道でも約 20 µs 増える。ヘッダを作って読み解く処理の分である。
- **差の大きさ**：HTTP まで載せると、Unix ソケットと TCP の差は約1.6倍に縮まる。p99 のばらつきは TCP + HTTP が最も大きい。
- **前提**：接続を使い回した測定なので、TCP のハンドシェイクのコストは入っていない。接続を毎回作り直すと、TCP との差はさらに広がる。また、Node のイベントループのコストも含んだ値である。

数値は環境に強く依存する。C で書いた場合や Linux では、絶対値も比率も変わりうる。実際のアプリでは、アプリ自身の処理時間のほうがずっと大きいことが多く、その場合は通り道の差はほとんど見えなくなる。

## 6.5 Unix ソケットの上で HTTP を使う理由

メリットは2つに分けられる。

**生のバイト列ではなく HTTP を使うメリット**

- **既存の道具がそのまま使える**：`curl --unix-socket /var/run/docker.sock http://localhost/containers/json` のように確認やデバッグができる。各言語の HTTP ライブラリもそのまま使える。
- **取り決めを作らずに済む**：メッセージの区切り方、リクエストとレスポンスの対応、エラーの表し方（ステータスコード）、パスによる振り分け、バージョン管理（`/v1.43/...`）を自分で設計しなくてよい。
- **リモートにもそのまま出せる**：同じ API を TCP + TLS で公開し直せる。Docker の `-H tcp://...` がその例である。

**TCP ではなく Unix ソケットを使うメリット**

- 速い。6.4 の測定では、HTTP 同士で p50 が 43 µs から 26 µs に下がった。
- ポートを開けないので、ネットワークから届かず、ポートスキャンでも見えない（[10章](10-port-scan.md)）。ポートの衝突も起きない。
- ファイルのパーミッションで、誰が接続できるかを決められる（[1章](01-unix-domain-socket.md)）。
- 接続してきた相手プロセスの uid や pid をカーネルから取れる（Linux の `SO_PEERCRED`、macOS の `getpeereid`）。パスワードなしで相手を認証できる。

**代償**：生のバイト列と比べて、1往復あたり約 20 µs（6.4 の測定値）と、ヘッダの分のバイト数が増える。Docker、containerd、systemd などのローカル API が Unix ソケットの上で HTTP（または gRPC）を使うのは、この代償よりメリットのほうが大きいからである。
