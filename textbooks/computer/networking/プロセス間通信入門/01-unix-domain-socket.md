# 1. Unix ドメインソケット

## 1.1 ルーティングされない通信

Unix ドメインソケットは、同じマシン（同じカーネル）の中にあるプロセス同士の通信に使う。IP や TCP の層を通らないので、ルーティングはされない。

データはファイルに書き込まれるわけではない。送信側プロセス → カーネル内のバッファ → 受信側プロセス、とメモリ上でコピーされる。ループバック（127.0.0.1）の TCP よりも処理が少ないので速い。

## 1.2 ソケットファイルは「住所」と「鍵」

`/var/run/docker.sock` のようなソケットファイルには、中身がない。`ls -l` で見るとサイズは 0、種類は `s`（socket）と表示される。ロジックもルールも持っていない。

それでも重要なのは、次の2つの役割があるからだ。

- **住所（ランデブーポイント）**：関係のない2つのプロセスが落ち合うには、お互いが知っている名前が必要になる。TCP では IP とポート番号がその役割をし、Unix ソケットではファイルパスがその役割をする。
- **鍵（アクセス制御）**：ファイルシステム上にあるので、所有者・グループ・パーミッションがそのまま効く。例えば `docker.sock` が `root:docker 660` なら、docker グループのユーザーしか接続できない。

実際のロジックはサーバープロセス側にあり、ソケットファイルはそのサーバーの入口を示す表札にすぎない。電話番号そのものに機能はないが、番号がないと電話をかけられないのと同じである。

## 1.3 ソケットファイルは接続時にしか使われない

ソケットファイルが使われるのは、接続を始めるときだけだ。一度つながったら、通信はカーネル内のバッファを通る。そのため、接続中にファイルを削除しても既存の接続はそのまま続く。困るのは、新しく接続しようとするクライアントだけである。

## 1.4 ソケットファイルがないとき

クライアントは接続先を見つけられず、`connect()` が `No such file or directory`（ENOENT）で失敗する。Docker なら `Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?` と表示される。

主な原因は次のとおり。

- サーバー（デーモン）が起動していない。ソケットファイルはサーバーが `bind()` したときに作られる。
- OS の再起動で消えた。`/var/run` は通常 tmpfs なので、再起動すると中身が消える。
- サーバーとクライアントでパスの設定が食い違っている。
- コンテナからホストのソケットを使うときに、`-v /var/run/docker.sock:/var/run/docker.sock` のマウントを忘れている。

逆に、サーバーが異常終了すると古いソケットファイルが残ることがある。この場合、次の起動時の `bind()` が `Address already in use` で失敗する。多くのサーバーは、起動時に古いファイルを `unlink` してから作り直す。

## 1.5 ファイル名でなくてもよい

ソケットに名前を付ける方法は、ファイルパスだけではない。

| 方法 | 内容 |
|---|---|
| 抽象名前空間ソケット（Linux のみ） | パスの先頭を NUL バイトにすると、ファイルを作らずカーネル内の名前だけで待ち受ける。`ss -x` では `@name` と表示される。プロセス終了で名前も消える |
| `socketpair()` | 名前のない接続済みペアを作り、`fork` した親子プロセスで使う |
| fd の受け渡し | systemd のソケットアクティベーションのように、開いたソケットそのものを渡す |

それでもファイルパスが標準なのは、ファイルシステムの仕組みをそのまま使えるからだ。

- パーミッションでアクセス制御ができる。抽象名前空間には権限がなく、同じネットワーク名前空間のプロセスなら誰でも接続できる。
- 階層で整理でき、`ls` や `rm` などの既存ツールで扱え、コンテナには bind mount で渡せる。
- 新しい名前空間を作らずに済み、「すべてをファイルとして扱う」という Unix の設計方針に合う。
