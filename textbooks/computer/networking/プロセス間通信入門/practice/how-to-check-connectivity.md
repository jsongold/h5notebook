# 実習：WAN の接続不良から根本原因を絞る

「インターネットにつながらない」を一つの故障として扱わない。**どの端末から、どの宛先へ、どの段階まで成功するか**を比べて、最後に成功した地点と最初に失敗した地点の間を調べる。この実習では、家庭や小規模オフィスから外向きに接続する場合を中心に扱う。後半には、WAN 側から自宅サーバーへ接続する場合もある。

## 1. 最初に記録すること

障害が起きている間に、時刻、端末、接続方法（Wi-Fi / 有線）、宛先の名前とポート、エラーメッセージを記録する。同じ宛先を**別の端末**と**別の回線**（例：スマートフォンのモバイル回線）から試す。比較する際は同じ時刻・同じ URL・同じポートを使う。

| 比較結果 | まず疑う範囲 |
|---|---|
| 1台だけ失敗 | 端末の IP 設定、VPN、プロキシ、ホストのファイアウォール |
| 同じ LAN の全端末で失敗 | ルーターの WAN 接続、上流回線、共通 DNS |
| 1つの宛先だけ失敗 | 宛先サービス、その経路、宛先ごとの DNS やフィルタ |
| 同じ宛先が別回線では成功 | 元の回線・ルーター・経路。宛先が元の送信元 IP を拒否している可能性もある |

これらは仮説であり、比較だけで原因を確定しない。設定を変える前に、以下の読み取り中心の操作で証拠を集める。

## 2. 操作：失敗地点を順に探す

以下の `example.com` は、実際に失敗しているホスト名に置き換える。HTTPS 以外ならポートとプロトコルも合わせる。macOS と Linux でコマンドが違う箇所は分けて示す。

### ① LAN とデフォルト経路

```sh
# macOS: デフォルトゲートウェイと、外向き通信で選ばれる経路
route -n get default
route -n get 1.1.1.1

# Linux
ip route
ip route get 1.1.1.1
```

出力の `gateway` / `via` とインターフェースを記録する。意図しない VPN や別のインターフェースが選ばれていないかを見る。表示された**ゲートウェイの IP**に `ping -c 3 ゲートウェイのIP` を送る。ここで失敗したら、まず端末からルーターまで（Wi-Fi、有線、IP 設定）を調べる。ただしゲートウェイが ICMP に応答しない設定なら、ping の失敗だけでは判断できない。

### ② 名前解決と HTTPS を別々に確認

```sh
dig example.com A
dig example.com AAAA
curl -4 -v --connect-timeout 3 --max-time 10 https://example.com/ -o /dev/null
curl -6 -v --connect-timeout 3 --max-time 10 https://example.com/ -o /dev/null
```

`dig` の応答に含まれる IP、応答した DNS サーバー、エラーを記録する。`curl -v` では「名前解決」「接続」「TLS」「HTTP 応答」のどこまで進んだかを見る。macOS では `dig` とアプリが参照する DNS 経路が異なる場合があるので、`curl` の結果とも照合する。`curl -6` は IPv6 経路がない環境では失敗してよい。対象サイトに AAAA レコードがない場合も IPv6 の比較には使えない。

DNS を迂回して試すときは、正常に解決できた別回線などで得た**その宛先の IPv4 アドレス**を使う。IP を URL に直書きせず、ホスト名と TLS の検証を保つ。

```sh
curl -4 -v --connect-timeout 3 --max-time 10 \
  --resolve example.com:443:取得したIPv4アドレス \
  https://example.com/ -o /dev/null
```

通常の `curl` が失敗し、`--resolve` で成功すれば、DNS の応答やキャッシュが有力になる。ただし、DNS が複数の IP を返すサービスでは、IP ごとの障害もあり得る。逆に両方失敗しても DNS が正常とは限らない。

### ③ TCP の先と、ルーターの WAN 状態

```sh
nc -vz -G 3 example.com 443    # macOS
nc -vz -w 3 example.com 443    # Linux
```

接続が成功してもページが開かないなら、TCP より先の TLS、HTTP、アプリケーションを調べる。接続がタイムアウトする場合は、ルーターの管理画面で WAN 接続状態、WAN 側 IP、ゲートウェイ、障害ログを**閲覧**する。WAN 側 IP が未取得なら、ルーターより上流（回線・ISP・接続設定）が有力になる。WAN 側 IP があっても上流障害は否定できない。

必要なら `traceroute example.com`（Linux では環境により `tracepath example.com`）で経路を眺める。途中の `*` はそのルーターが検査パケットに返答しないだけかもしれない。**そのホップが故障した証拠にはしない**。同じ宛先への実際の接続結果と、別回線での結果を優先する。

## 3. 診断ドリル

各問で、(1) 最も有力な故障範囲、(2) そう判断した観測、(3) 確定に近づく次の操作を答える。解答は下にある。

### ドリル A：ルーターまで届くか

- ノート PC だけ Web サイトを開けない。ほかの端末は同じ Wi-Fi で開ける。
- PC の `ip route get 1.1.1.1` は `via 192.168.1.1` と表示する。
- PC から `192.168.1.1` への ping は失敗する。ルーターの管理画面も開けない。

### ドリル B：名前だけ失敗する

- 同じ LAN の端末で `dig shop.example A` はタイムアウトする。
- 通常の `curl https://shop.example/` も名前解決エラーになる。
- 別回線で調べた `shop.example` の IPv4 アドレスを `curl --resolve` に渡すと HTTPS 応答が返る。
- ルーターの WAN 状態は接続済みで、ほかの IP 宛ての HTTPS は成功する。

### ドリル C：WAN の出口

- LAN 内の全端末で複数の外部サイトがタイムアウトする。ゲートウェイの管理画面は開ける。
- ルーターの WAN 画面は「未接続」で、WAN 側 IP がない。
- スマートフォンのモバイル回線では同じサイトが開ける。

### ドリル D：ポートまでは開いている

- `nc -vz app.example 443` は成功する。
- `curl -v https://app.example/` は TLS のハンドシェイク後に HTTP `503` を受け取る。
- 別回線でも同じ `503` になる。

### ドリル E：IPv4 と IPv6 の差

- `dig dual.example A` と `dig dual.example AAAA` は両方成功する。
- `curl -4 https://dual.example/` は成功し、`curl -6` はタイムアウトする。
- 同じ LAN の複数端末で再現し、別回線の IPv6 では成功する。

### ドリル F：外から自宅サーバーに入れない

- LAN 内から `192.168.1.10:8080` へ接続でき、サーバーは LAN 側アドレスで待ち受けている。
- ルーターには TCP 8080 → `192.168.1.10:8080` の転送設定がある。
- ルーターの WAN 側 IPv4 は `100.72.4.8`。外部の IP 確認サイトでは別の IPv4 が表示される。
- モバイル回線から外部表示の IPv4 の TCP 8080 には接続できない。

## 4. 解答と次の操作

| 問 | 最も有力な故障範囲と根拠 | 次の操作 |
|---|---|---|
| A | その PC とルーターの間。ほかの端末は正常で、ゲートウェイにも届かない | Wi-Fi の接続先、端末の IP・サブネット、VPN、インターフェースを確認する。ping のみでなく管理画面への TCP 接続でも確認する |
| B | DNS。名前解決だけ失敗し、同じホスト名と IP を指定した HTTPS は成功する | 端末とルーターで設定された DNS サーバー、別の DNS サーバーからの応答、DNS 障害ログを比較する |
| C | ルーターの WAN 接続から ISP まで。LAN は使えるが、ルーターが WAN 側 IP を持たない | 回線終端装置の状態、ルーターの WAN ログ、ISP の障害情報を確認する。契約や接続設定の変更は証拠を取ってから行う |
| D | 宛先の HTTP サービスかその手前のプロキシ。TCP と TLS は通過済みで、HTTP `503` が返っている | 宛先側の稼働状況、プロキシ・アプリのログ、`Retry-After` や応答ヘッダーを確認する |
| E | 元の回線の IPv6 経路、ルーターの IPv6 設定、またはその経路上の問題 | ルーターの IPv6 WAN 状態と端末の IPv6 デフォルト経路を調べ、別の IPv6 宛先でも再現するか比べる |
| F | ISP 側の共有 IPv4（CGNAT）が有力。`100.72.4.8` は共有アドレス帯 `100.64.0.0/10` にある | ISP の接続方式・公開 IPv4 の有無を確認する。ルーターだけのポート転送では外から届かない可能性が高い。IPv6 の公開設定や VPN / 中継方式を検討する |

どのドリルでも、**タイムアウトだけで故障箇所を断定しない**。再現する端末・回線・宛先を増やし、最後に成功した段階から範囲を狭める。NAT とファイアウォールの関係は[11章](../11-nat.md)と[12章](../12-firewall.md)、接続前後のテーブルは[13章](../13-tables-overview.md)を参照。
