# 10. ポートスキャン

## 10.1 何をしているか

ポートスキャンは、カーネルの待ち受けソケットテーブル（[9章](09-listening-table.md)）を外から確かめる行為である。スキャナーは相手のマシンのポートに次々と接続要求（SYN）を送り、返ってくる反応でポートを3種類に分ける。

| 返ってくる反応 | カーネルの中で起きたこと | 判定 |
|---|---|---|
| SYN/ACK | 待ち受けソケットテーブルにそのポートがあった（`listen` しているプログラムがいる） | open |
| RST | テーブルにない。カーネルが「誰も待っていない」と返した | closed |
| 何も返らない | ファイアウォールが途中で捨てた | filtered |

## 10.2 なぜセキュリティで重要か

open のポートが1つあるということは、そのポートの向こうに、ネットワークから来たデータを読むプログラムがいるということである。そのプログラムにバグや脆弱性があれば、そこが入口（攻撃面）になる。そのため攻撃者は、まずポートスキャンで入口の一覧を作り、次にポートごとのソフトウェアとバージョンを調べる。

## 10.3 見えるもの、見えないもの

- **Unix ソケットはスキャンできない**：ポートがなく、ネットワークから届かないからである。ローカル API に Unix ソケットが使われる理由の1つである（[6章](06-performance.md)）。
- **`127.0.0.1` で待ち受けているポート**：ループバックでしか受け付けないので、外からのスキャンでは見えない。
- **`0.0.0.0` で待ち受けているポート**：すべてのインターフェースで受け付けるので、外から見える。

## 10.4 自分のマシンを確認する

自分のマシンで何が open かは、内側から確認できる。

```
netstat -an -p tcp | grep LISTEN
```

`*.8082 LISTEN` のように、どのポートでどのアドレスに待ち受けているかが見える（`*` は `0.0.0.0`）。

nmap などの外からスキャンするツールは、自分が管理しているか、許可を得たマシンにだけ使うこと。

## 10.5 SYN は誰が送ってくるのか

宛先が `10.0.0.1:5432` の SYN が届くのは、送った側がその IP を宛先として指定したからである。ただし、次の3点に注意する。

- **相手を知っているとは限らない**：攻撃者は、狙う相手を調べてから送るとは限らない。IP アドレスの範囲全体に、機械的に SYN を投げているだけのことが多い。インターネットに公開されたアドレスには、こうした無差別なスキャンが常に届いている。
- **`10.0.0.1` はプライベート IP である**：`10.0.0.0/8` はプライベートアドレスの範囲（RFC 1918）なので、インターネットから直接この宛先には届かない。届くのは、同じ LAN、同じクラウドの VPC、または同じ VPN の中にいる相手からである。インターネット側から見えるのはルーターのグローバル IP の方で、ルーターは外から始まった接続を通常は通さない（[11章](11-nat.md)、[12章](12-firewall.md)）。
- **送信元は偽装できる**：SYN の送信元 IP は書き換えられるので、届いたパケットの送信元が本当の送り主とは限らない。偽装すると返事（SYN/ACK）は偽の送信元に返るので、偽装した側はスキャンの結果を受け取れない。それでも、本物のスキャンを隠すためのおとり（デコイ）として使われることがある。

PostgreSQL を `127.0.0.1` だけで待ち受けていれば、同じ LAN の中から SYN が届いても closed になる。

## 10.6 自分の PC にもスキャンは来ているか

一般的には、スキャンはネットワークの入口までは常に来ているが、PC 本体まではほとんど届いていない。

| 環境 | スキャンが届く先 | PC まで届くか |
|---|---|---|
| 家庭やオフィスのルーターの後ろ | ルーターのグローバル IP | 届かない。NAT とファイアウォールが外から始まった接続を止める（[11章](11-nat.md)、[12章](12-firewall.md)）。例外はポートフォワーディングや UPnP で穴が開いている場合 |
| カフェやホテルの公衆 Wi-Fi | 同じ LAN にいる他人の機器から PC へ直接 | 届く。これが一番現実的なリスクである |
| IPv6 | PC 自身がグローバルアドレスを持つことがある | 多くのルーターは外から始まる接続を初期設定で遮断している。また、アドレス空間が広すぎて、無差別に探すスキャンは事実上できない |

検証に使った Mac では、nginx が `*:80`、別のプロセスが `*:8082` と `*:61568` で待ち受けていた。どれもすべてのインターフェースで待ち受けているので、公衆 Wi-Fi のように同じ LAN に他人がいる場所では、これらのポートが外から見える。開発用であれば、`127.0.0.1` だけで待ち受けるように設定するか、macOS のファイアウォール（システム設定 → ネットワーク → ファイアウォール）を有効にするのが安全である。

## 10.7 クラウドの VM を公開する場合

グローバル IP を持った VM は、公開してすぐに無差別なスキャンの対象になる。特に、SSH（22番）へのパスワード総当たりのログイン試行は、公開したその日からログに並ぶのが普通である。具体的な頻度は IP アドレスの範囲や時期によって変わる。

スキャンでよく狙われるポートは次のとおりである。

| ポート | 用途 |
|---|---|
| 22、3389 | SSH、RDP（リモートログイン） |
| 80、443 | Web |
| 3306、5432、6379、27017 | データベースや Redis など。認証なしで公開されてしまう事故が多い |

ただし、クラウドではファイアウォールのない状態にはまずならない。GCP の VPC ファイアウォールは、外から入ってくる通信を初期状態で拒否する（暗黙の拒否ルール）。AWS のセキュリティグループも、受信は初期状態で拒否である。そのため、自分で許可ルールを足したポートだけが外から見える。

気をつけたいのは、送信元を `0.0.0.0/0`（すべての IP アドレス）にして許可してしまうケースである（[12章](12-firewall.md)）。例えば SSH を IAP 経由だけで使う GCP の VM なら、22番の許可を IAP のアドレス範囲（`35.235.240.0/20`）に絞る。そうすれば、外からのスキャンには closed や filtered として見える。逆に、`0.0.0.0/0` から 22番を許可するルールが残っていると、総当たりのログイン試行の対象になる。GCP では `gcloud compute firewall-rules list` でルールを読み取りだけで確認できる。

## 10.8 判定とテーブルの対応

外からの SYN は、プロセスに届くまでに複数のテーブルを順に通る（全体の図は[13章](13-tables-overview.md)）。スキャンの3つの判定は、どこで止まったかに対応する。

| 止まった場所 | 判定 |
|---|---|
| ファイアウォールルールで捨てられた | filtered |
| ファイアウォールは通ったが、待ち受けソケットテーブルに載っていない | closed |
| 待ち受けソケットテーブルに載っている | open |
