# 13. 表の整理

## 13.1 テーブルの呼び分け

ここまでに出てきた「表」は、すべて別のものである。この教科書では次の名前で呼び分ける。共通しているのは、どれも「パケットや呼び出しから値を取り出してテーブルを引き、どうするかを決める」という仕組みだという点である。

| 呼び名 | 英語名・実装名 | 場所 | キー → 値 | 中身の作られ方 |
|---|---|---|---|---|
| ファイアウォールルール | ruleset / ACL（GCP の VPC firewall rules、AWS のセキュリティグループ、Linux の nftables） | クラウドの VPC、ルーター、ホスト | 送信元・宛先・ポートの条件 → 許可 / 拒否 | 人が書く（固定） |
| 接続追跡テーブル | conntrack table（Linux）、state table（BSD の pf） | ルーター、ファイアウォール | 4つの組 → 接続の状態 | 通信に応じて自動で増減する |
| NAT 変換テーブル | NAT mapping | ルーター | 外の IP・ポート ↔ 中の IP・ポート | 送信元 NAT は自動、ポートフォワーディング（宛先 NAT）は人が書く |
| 待ち受けソケットテーブル | listening hash（Linux の `lhash2`） | 各機器のカーネル | 自分の IP・ポート → 待ち受けソケット | `listen()` で登録される |
| 確立済み接続テーブル | established hash（Linux の `ehash`） | 各機器のカーネル | 4つの組 → 接続済みソケット | 接続の確立で登録される |
| ポート使用状況テーブル | bind hash（Linux の `bhash`） | 各機器のカーネル | ポート → それを使っているソケット | `bind()` で登録される |
| fd テーブル | file descriptor table | 各プロセス | fd 番号 → ソケットなどのカーネルオブジェクト | `socket()`、`accept()`、`open()` で登録される |
| ルーティングテーブル | routing table | 各機器のカーネル、ルーター | 宛先ネットワーク（CIDR） → 次に渡す先（ゲートウェイ）と出ていくインターフェース | インターフェースの設定や DHCP で自動、または人が書く。ルーター同士では経路の情報を交換して作る |
| ARP テーブル | ARP cache（IPv6 では neighbor cache） | 各機器のカーネル、ルーター | 同じネットワークの中の IP アドレス → MAC アドレス | ARP の問い合わせと応答で自動で登録され、時間切れで消える |

- 各章との対応：待ち受けソケットテーブル、確立済み接続テーブル、ポート使用状況テーブルは[8章](08-tcp-loopback-and-port.md)と[9章](09-listening-table.md)、NAT 変換テーブルは[11章](11-nat.md)、ファイアウォールルールと接続追跡テーブルは[12章](12-firewall.md)で扱った。ルーティングテーブルと ARP テーブルは 13.4 で概要だけ扱う。
- **NAT 変換テーブルと接続追跡テーブルの関係**：Linux ベースのルーターでは、NAT の変換情報は接続追跡テーブルの各行の中に一緒に記録されている。そのため、実装上は1つのテーブルである。役割が違うので、説明では分けて呼ぶ。

カーネル内部の名前（`lhash2` など）は記憶にもとづく。正確には Linux のソースの `include/net/inet_hashtables.h` で確認すること（[9章](09-listening-table.md)と同じ注意）。

## 13.2 1つのパケットが通るテーブル

1つの SYN が外から VM のプログラムに届くまでに、順番に通るテーブルを並べると次のようになる。

```
インターネットからの SYN（宛先: VM の IP:22）
  │
  ├─ ① ファイアウォールルール（クラウドの VPC やルーター）
  │     「送信元・ポートは許可されているか？」 → いいえなら捨てる（filtered）
  │
  ├─ ② 接続追跡テーブル / NAT 変換テーブル（ルーター。家庭の場合）
  │     「既存の接続の続きか？ どの機器に渡すか？」
  │
  ── ここから VM（または PC）のカーネルの中 ──
  │
  ├─ ③ 確立済み接続テーブル（キー: 4つの組）
  │     「既存の接続か？」 → あれば、その接続済みソケットへ
  │
  ├─ ④ 待ち受けソケットテーブル（キー: 自分の IP + ポート）
  │     「待ち受けているソケットはあるか？」 → なければ RST（closed）
  │     → あれば受付キューへ（open）
  │
  └─ ⑤ fd テーブル（プロセスの中）
        accept() で接続済みソケットに新しい fd 番号が割り当てられ、
        プロセスはその fd で read() / write() する
```

- **ソケットの話で出てきたテーブル**：③〜⑤である。機器自身のカーネルとプロセスの中にあり、「届いたパケットを、どのソケットに渡すか」を決める。
- **ファイアウォールの話で出てきたテーブル**：①と②である。機器の手前（境界）にあり、「そもそも通すかどうか」を決める。
- この図は、どちらのテーブルを通るかを示したものである。Linux ベースのルーターの中での細かい順番（宛先 NAT が先で、ファイアウォールの判定が後）は[12章](12-firewall.md)を参照。
- ポートスキャンの3つの判定も、この図で説明できる。①で捨てられれば filtered、④に載っていなければ closed、④に載っていれば open である（[10章](10-port-scan.md)）。

## 13.3 図に出てこないテーブル

ポート使用状況テーブルは、この図には出てこない。このテーブルは、パケットを受信するときには引かれない。`bind()` のときに「このポートは空いているか」を確かめるためだけに使われる（`Address already in use` の判定）。

## 13.4 ①より前：SYN が VM の IP に届くまで（次に学ぶ範囲）

13.2 の図は「SYN が VM の IP に届いた」ところから始まっている。そこまでどうやって運ばれてきたかは入っていない。この図でカバーできているのは、L4（TCP のポート、接続、ハンドシェイクの入口）、ファイアウォールと NAT、カーネルの中のソケットとプロセスの関係である。

ネットワークの基礎として残っているのは次のテーマである。ここでは概要だけを示し、詳しくは次に学ぶ範囲とする。

| テーマ | 内容 | 出てくるテーブル |
|---|---|---|
| DNS | 名前（example.com）から IP アドレスを引く | DNS のキャッシュ |
| IP アドレスとサブネット | `10.0.0.0/8` のような CIDR の読み方。同じネットワークか、外かの判定 | なし |
| ルーティング（L3） | パケットがルーターを次々と渡って、宛先の IP まで運ばれる仕組み | ルーティングテーブル |
| L2（Ethernet / Wi-Fi） | 同じネットワークの中で、IP アドレスから MAC アドレスを引いて届ける | ARP テーブル |
| TCP の中身 | ハンドシェイク、再送、フロー制御（届いた後の信頼性） | なし |
| UDP と TLS | 接続のない通信と、暗号化 | なし |

ルーティングテーブルと ARP テーブルを 13.2 の図の①の前につなげると、送信元を出てから宛先のプロセスに届くまでを、テーブルを引く連なりとして最初から最後まで描ける。

```
送信元のプロセス
  → DNS で宛先の名前から IP を引く
  → ルーティングテーブル：次に渡す先を決める
  → ARP テーブル：次に渡す先の MAC アドレスを引く
  → （ルーターごとに、ルーティングテーブルと ARP テーブルを引いて次へ渡す）
  → 13.2 の ①〜⑤
  → 宛先のプロセス
```
