# ECC は環境一式、agent-skills は小さな手順書集

目的：ECC (affaan-m/ECC, npm ecc-universal) と addyosmani/agent-skills を、コードの中身・依存関係・Claude Code が扱えるかの観点で比較し、採用箇所を示す。

両者は種類が違う。**agent-skills は実行コードを持たない markdown 中心の手順書集**（skill 25、agent 4、command 9、checklist 7）で、**ECC は skill 293・agent 68・command 94・hook 24 に加え、Node インストーラ、manifests、MCP テンプレート、Rust 製 TUI まで含む「環境構築システム」**である。Claude Code から見た常時コンテキスト負荷は、agent-skills が約 3k token、ECC は profile により約 17k（minimal）から約 37k（full）で、full は skill 一覧の予算（コンテキストの 1%）を超えて説明文が削られる見込みである。依存関係はどちらも frontmatter に宣言がなく、本文中の名前参照（暗黙）が中心である。明示的な宣言があるのは ECC の install manifests と hooks の sidecar だけである。整合性を保つ仕組みは両者とも CI の検証スクリプトで、agent-skills は全体を把握しやすく、ECC は registry と CI を頼りに触る規模である。採用するなら、agent-skills の skill 設計（構造と anti-rationalization 表）と、ECC の一部の hook・skill を個別に取り込むのが妥当である。なお token 数はすべて文字数 / 4 の概算で、実行時の `/context` 計測や実インストールは行っていない。

## 何を出荷しているか：手順書集と環境システム

agent-skills は、25 の SKILL.md（合計 7,494 行、1 本あたり平均約 300 行、lint 上限 500 行）を核に、reviewer 人格 4 つ、slash command 9 個、共有 checklist 7 つを持つ。追跡ファイルは 208、hook スクリプトは 4 本（session-start、sdd-cache の pre/post、simplify-ignore）で、`hooks.json` は存在せず、プラグインは hook を登録しない ([agent-skills overview](https://github.com/addyosmani/agent-skills/blob/main/README.md), [session-start.sh](https://github.com/addyosmani/agent-skills/blob/main/hooks/session-start.sh))。実行コードは検証・eval 用の Node スクリプトだけで、`package.json` もインストーラもない。

ECC は、追跡ファイル約 4,200、npm パッケージは **2,615 ファイル / 17.7 MB**、bin 6 個、実行時依存 4 個（ajv, sql.js, js-yaml, @iarna/toml）である ([package.json](https://github.com/affaan-m/ECC/blob/main/package.json))。内容は、agent 68（言語別 reviewer や build resolver を多数含む）、skill 293（言語・フレームワーク約 100 本以上に加え、医療・物流・DeFi・動画生成などの業種別）、command 94（README 上は skills-first への移行に伴う「legacy shim」扱い）、rules 122 ファイル、MCP テンプレート 33 サーバである ([features 調査](https://github.com/affaan-m/ECC/blob/main/AGENTS.md), [mcp-servers.json](https://github.com/affaan-m/ECC/blob/main/mcp-configs/mcp-servers.json))。さらに `ecc2/`（Rust の TUI）、Python の dashboard、plan-canvas のローカルサーバなど、実行系のコードを別途持つ。

skill の書き方も対照的である。agent-skills は Overview / When to Use / Process / Common Rationalizations / Red Flags / Verification という固定構造を linter で強制し、「もっともらしい言い訳」への反論表で agent の手抜きを抑える ([CLAUDE.md](https://github.com/addyosmani/agent-skills/blob/main/CLAUDE.md))。command は skill を呼ぶだけの薄い層（本文が「agent-skills:<skill> を起動せよ」）で、`/ship` は code-reviewer・security-auditor・test-engineer を並列に走らせて統合する ([ship.md](https://github.com/addyosmani/agent-skills/blob/main/.claude/commands/ship.md))。ECC の skill は 100〜900 行で形式が揃っておらず、frontmatter の `metadata` を持つのは 266 本、agent は `tools` / `model` を必ず持つ（68/68）一方、command は `description` のみである ([features 調査 §5](https://github.com/affaan-m/ECC/blob/main/docs/COMMAND-REGISTRY.json))。agent-skills の agent は `name` / `description` のみで、`tools` も `model` も指定しないため、親の権限をそのまま継承する（継承の挙動自体は今回未確認）。

## skill・agent・command の中身は、どちらも命令文の markdown

実体はどちらも frontmatter 付きの markdown プロンプトで、コードではない。agent-skills の skill は、`description` に「Use when ...」を含め、本文は Overview / When to Use / 手順 / Common Rationalizations / Red Flags / Verification の順に並ぶ。例えば `test-driven-development`（398 行）は「Step 1: RED — Write a Failing Test. Write the test first. It must fail.」と手順を刻み、反論表に「I'll write tests after the code works」→「You won't. And tests written after the fact test implementation, not behavior.」を置き、Red Flag に「テストコマンドを変更なしで 2 回連続実行する」を挙げ、末尾は `- [ ] No tests were skipped or disabled` のようなチェックボックスで閉じる ([test-driven-development/SKILL.md](https://github.com/addyosmani/agent-skills/blob/main/skills/test-driven-development/SKILL.md))。agent（`code-reviewer`）は「You are an experienced Staff Engineer」で始まり、5 観点の質問リスト、重大度ラベル（Critical / Required / Optional / Nit）、出力テンプレート、「テストを先に見る」などの番号付き規則、そして「他の persona から呼ぶな、orchestration は command の役目」という Composition 節を持つ ([code-reviewer.md](https://github.com/addyosmani/agent-skills/blob/main/agents/code-reviewer.md))。command（`review.md`、846 bytes）は「Invoke the agent-skills:code-review-and-quality skill. Review the current changes ...」の数行で、重大度名は Critical / Important / Suggestion と、agent 側の語彙とずれている ([review.md](https://github.com/addyosmani/agent-skills/blob/main/.claude/commands/review.md))。`/build auto` のような大きい command は、`$ARGUMENTS` でモードを分け、SPEC 必須、`git status --porcelain` でクリーンな基準を確認、承認ゲートは 1 回、以降はタスクごとに 1 commit という段取りである ([build.md](https://github.com/addyosmani/agent-skills/blob/main/.claude/commands/build.md))。

ECC の skill（例 `tdd-workflow`、583 行）は、`name`、長い 1 文の `description`、`argument-hint`、`metadata.origin: ECC` の frontmatter に続き、`## When to Activate` の箇条書きと、plan の出力を「untrusted planning input」として扱う `## Plan Handoff` を置く ([tdd-workflow/SKILL.md](https://github.com/affaan-m/ECC/blob/main/skills/tdd-workflow/SKILL.md))。agent（`code-reviewer`、323 行）は `tools: Read, Grep, Glob, Bash` と `model: sonnet` を指定し、本文は「Prompt Defense Baseline」（役割を変えない、秘密を出さない、外部内容を信用しない）で始まる。これは prompt の文言で、強制機構ではない。`description` に「MUST BE USED for all code changes」があり、常時ロードされる説明文が委譲を押しやすい書き方である ([code-reviewer.md](https://github.com/affaan-m/ECC/blob/main/agents/code-reviewer.md))。command（`plan.md`、206 行）は「既定ではインラインで実行し Task ツールを呼ばない（agent ファイルの無い plugin 導入でも動かすため）」と述べ、番号付き手順の末尾に「利用者の CONFIRM まで一切コードに触れない」を置く ([plan.md](https://github.com/affaan-m/ECC/blob/main/commands/plan.md))。rule は `rules/common/coding-style.md` が frontmatter なし（常時ロード）で「ALWAYS create new objects, NEVER mutate」と WRONG / CORRECT の擬似コードを載せ、言語別 rule は `paths:` glob を先頭に持ち「common を拡張する」と書く（122 ファイル中 111 が path 限定）([coding-style.md](https://github.com/affaan-m/ECC/blob/main/rules/common/coding-style.md))。CRITICAL、MUST BE USED、ALWAYS / NEVER といった強い語が多く、eager に呼び出される方向に効く（推論）。また issue #2906 は、94 command の説明に「いつ使うか」の trigger 句が 0 件だと指摘している。

## hook と installer が実際にやること

差が最も大きいのはここである。agent-skills には installer がなく、`/plugin marketplace add` と `/plugin install` で入り、settings.json を書き換えるコードは無い。hook は利用者が JSON を手で貼る方式で、危険度が高いのは simplify-ignore だけである。これは Read 時にソースの該当ブロックをプレースホルダに置換し、Stop で復元する。異常終了すると作業ツリーにプレースホルダが残りうるが、今回は実行しておらず、テストファイルがあることを確認したにとどまる ([hooks/simplify-ignore.sh](https://github.com/addyosmani/agent-skills/blob/main/hooks/simplify-ignore.sh))。sdd-cache は WebFetch の結果を `.claude/sdd-cache/` に保存し、ETag で再検証し、304 なら WebFetch を exit 2 で止めて保存内容を返す。

ECC の `hooks/hooks.json` は **7 イベントに 24 個**の hook を登録し、すべて `node -e` の bootstrap 経由で ECC のスクリプトを利用者権限で実行する。`ECC_HOOK_PROFILE`（minimal / standard / strict）で絞れる ([hooks.json](https://github.com/affaan-m/ECC/blob/main/hooks/hooks.json), [hook-flags.js](https://github.com/affaan-m/ECC/blob/main/scripts/lib/hook-flags.js))。内容は次のとおりで、ワークフローに介入する。

- **GateGuard**：最初の Edit / Write で、影響範囲の説明と利用者指示の引用が済むまで exit 2 で拒否する。
- **config-protection**：既存の linter / formatter 設定の編集を止める。
- **mcp-health-check**：不調な MCP サーバへの呼び出しを止める。
- **観察系**：`.*` matcher の observe が全ツール呼び出しで走り、continuous-learning 用に記録する。
- **終了時**：pre-compact と session-end が `claude -p`（既定 haiku）で transcript を要約し、Stop 時に format と typecheck を最大 300 秒で回す。

各 hook の中身は具体的である。`pre-bash-dispatcher.js` は入力が `ECC_HOOK_INPUT_MAX_BYTES` を超えても、dispatcher が例外を出しても exit 2 で止める（fail-closed）ため、ECC 側のバグが全 Bash 拒否の障害になり、hook を切るまで直らない ([pre-bash-dispatcher.js](https://github.com/affaan-m/ECC/blob/main/scripts/hooks/pre-bash-dispatcher.js))。`block-no-verify.js` は git の `--no-verify` と `-c core.hooksPath=` を、`pre-bash-dev-server-block.js` は tmux 外の `npm run dev` 系（`$(npm run dev)` の包み形も）を exit 2 で止める。`pre-bash-commit-quality.js` は `git commit` 時に staged 内容を `git show` で読み、`console.log`・TODO・秘密のような正規表現を走査し、必要なら linter を回して重大なものを止める。GateGuard は `permissionDecision: 'deny'` を返し、状態を `~/.gateguard`（500 エントリ / 50 session 上限）に JSON で書き、状態書き込みに失敗した場合は再試行ループを避けて許可に倒す。`config-protection.js` は保護対象の設定ファイルへの Edit / Write を止めるが、新規作成は許す。**`stop-format-typecheck.js` は Stop 時に、その turn で編集した JS/TS に Biome `check --write` か Prettier `--write` を `spawnSync` で実行し、Edit ツールを経ずにソースを書き換える**ため、別の formatter 設定を持つ repo で意図しない差分が出うる。続けて `npx tsc --noEmit` も実行する。`observe.sh` は全ツール呼び出しを `observations.jsonl` に追記し（`tool_input` は 5,000 文字で切る）、key / token / secret / password 等の名前に一致するパターンを正規表現で伏せるが、これは best-effort で、パターン外の秘密はローカルに残る。`session-start.js` は前回の要約、instincts、学習済み skill、プロジェクト種別を `additionalContext`（上限は `ECC_SESSION_START_MAX_CHARS`）として毎 session 注入する。また hook の起動コマンドはすべて同形の `node -e "<inline resolver>"` で、`CLAUDE_PLUGIN_ROOT`、次に `~/.claude`、最後に plugin cache を探し、この `~/.claude` へのフォールバックが `CLAUDE_CONFIG_DIR` 別 profile での不具合（[#3266](https://github.com/affaan-m/ECC/issues/3266), [#3279](https://github.com/affaan-m/ECC/issues/3279)）の原因と考えられる（推論）。

書き込み先は `~/.claude/metrics/costs.jsonl`、`~/.gateguard`、`~/.local/share/ecc-homunculus` などのホーム配下で、`~/.claude` を含むパスを 101 ファイルが参照している ([gateguard-fact-force.js](https://github.com/affaan-m/ECC/blob/main/scripts/hooks/gateguard-fact-force.js), [cost-tracker.js](https://github.com/affaan-m/ECC/blob/main/scripts/hooks/cost-tracker.js), [llm-summary.js](https://github.com/affaan-m/ECC/blob/main/scripts/lib/llm-summary.js))。hooks 内に ECC 独自のサーバへの送信は grep では見つからなかったが、全スクリプトを行単位では読んでおらず、実行時のトレースもしていない。

agent-skills 側の hook も中身は単純である。`session-start.sh` は `using-agent-skills/SKILL.md` を jq で `hookSpecificOutput.additionalContext` に包んで出力し、jq が無ければ通知 JSON を出して exit 0 する。`sdd-cache-pre.sh` は `.tool_input.url` の sha256（128 bit に切詰め）をキーに `${CLAUDE_PROJECT_DIR}/.claude/sdd-cache/<hash>.json` を引き、origin へ If-None-Match で再検証して 304 のときだけキャッシュを返す（cache hit 時の応答の細部は未読）。`simplify-ignore.sh` は 1 本で 3 イベントを処理し、Read で退避して `simplify-ignore-start/end` ブロックを `BLOCK_<hash>` に置換し、Edit / Write 後に展開・再置換し、Stop で復元する（jq と shasum/sha1sum が必要）。マニフェストは薄く、`.claude-plugin/plugin.json` は commands・skills のディレクトリと `experimental.evals` を指すだけで、`marketplace.json` は `source: github` の 1 エントリである ([plugin.json](https://github.com/addyosmani/agent-skills/blob/main/.claude-plugin/plugin.json))。

installer は 2 系統ある。推奨は `npx ecc-universal setup` で、`claude plugin ...` CLI を呼んで `ecc@ecc` を導入し、`~/.claude/settings.json` の `pluginConfigs` に hook 設定を書く。さらに **`includeCoAuthoredBy` と `attribution` が未設定なら `"includeCoAuthoredBy": false` を書く**（commit / PR の Co-Authored-By 行が無効になる）([claude-plugin-setup.js](https://github.com/affaan-m/ECC/blob/main/scripts/lib/claude-plugin-setup.js), [claude-commit-attribution.js](https://github.com/affaan-m/ECC/blob/main/scripts/lib/claude-commit-attribution.js))。もう一つの `install.sh` は、`node_modules` が無ければ `npm install --ignore-scripts` を実行してから `install-apply.js` を呼ぶ。実処理は `scripts/lib/install/apply.js` で、計画は `copy-file` と `update-claude-settings` の 2 種の操作だけで、コピーは `fs.copyFileSync`（OpenCode 用は symlink を辿らない `writeFileNoFollow`）、宛先は `assertSafeInstallOperation` で検証する。hook の登録は `claude-settings.js` が、許可するイベントと hook 種別（command / http / prompt / agent）を固定集合で検証し、`${CLAUDE_PLUGIN_ROOT}` を実パスに書き換えたうえで、ロックを取って ID 単位にマージする。`includeCoAuthoredBy: false` の書き込みも同経路（`apply.js` の `shouldSetClaudeCommitAttributionPreference`）で、`docs/` 以外に書く claude / claude-project 導入なら既定で走る。結果として rules・agents・commands・scripts・skills が `~/.claude` にコピーされる。dry-run で計測した full profile の書き込みは、rules 122、agents 68、commands 94、scripts 242、skills 585 ファイル、`update-claude-settings` 1 回で、状態は `~/.claude/ecc/install-state.json` に残る。hook を含む場合は `--enable-hooks` / `--no-hooks` の明示が必須で、実行前に hook の能力（ソース書き換え、transcript の外部 LLM 送信、MCP の起動・停止など）が列挙される ([hook-consent.js](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/hook-consent.js))。permissions を書き換えるコードは grep で見つからなかった。

コードに起因する不整合も記録されている。repo の VERSION / README は 2.2.2 だが npm の latest は 2.2.1 で、README の `npx ecc-universal@2.2.2 setup` は 404 になる報告がある ([#3222](https://github.com/affaan-m/ECC/issues/3222), [#3203](https://github.com/affaan-m/ECC/issues/3203))。2.2.1 の tarball には `scripts/github-coordination.js` が入っておらず、公開済みの `/epic-*` command 7 本が動かない ([#3270](https://github.com/affaan-m/ECC/issues/3270))。`skills/frontend-slides/scripts/export-pdf.sh` のローカル HTTP サーバに path traversal があり、修正は 2.2.1 より後である ([#3101](https://github.com/affaan-m/ECC/issues/3101))。一方 agent-skills 側の記録された不整合は、`.codex-plugin/plugin.json` の説明が「24 workflows」で実数 25 とずれていること、`npx skills add --skill X` で個別導入すると `../../references/` へのリンクが切れること（[#361](https://github.com/addyosmani/agent-skills/issues/361)）、`commands/*.toml` を plugin の commands パスに含めた場合の Claude Code の挙動が未検証であること、の 3 点である。

## 依存関係は暗黙が主で、明示は ECC の manifests のみ

どちらも frontmatter に `requires` / `depends-on` 相当の欄がない。agent-skills は 25 skill のうち 15 が他 skill を本文中でバッククォート名として参照し（`using-agent-skills` は 9 skill へ振り分け）、command は `agent-skills:<skill>` と名指しし、共有 checklist は相対パスで参照する。構成則は「skill=手順、agent=人格、command=起動タイミング」で、agent が別の agent を呼ばない（並列 fan-out と統合のみ）と AGENTS.md に明記されている ([AGENTS.md](https://github.com/addyosmani/agent-skills/blob/main/AGENTS.md), [skill-lint.js](https://github.com/addyosmani/agent-skills/blob/main/scripts/lib/skill-lint.js))。dangling 参照は linter が警告する。

ECC で機械可読な宣言があるのは配布層である。`manifests/install-modules.json` は 38 module を持ち、module 間の `dependencies`（例：`framework-language` は rules-core・agents-core・commands-core・platform-configs に依存）と、全 293 skill のパスを記す。ただし依存は module 単位で、skill 単位ではない ([install-modules.json](https://github.com/affaan-m/ECC/blob/main/manifests/install-modules.json))。hook は `hooks.metadata.json` の sidecar（id、説明、matcher と command のハッシュ）で管理され、`validate-hooks.js` がずれを検出する。command から agent・skill への関係は生成物の `COMMAND-REGISTRY.json` にあるが、**94 command のうち agent を載せるのは 17、skill を載せるのは 40 で、本文の prose 走査では 36 command が agent を名指ししており、registry は過小**である（正規表現による概算）。skill 同士の参照は 26/293 と少なく、うち 14 は存在しない名前（一部はディレクトリ名の語で誤検出）を指す。多くの skill は独立で単体編集できるが、結合は次の 3 箇所に集中している。

- **hook と共有状態ファイル**：`~/.claude/metrics/costs.jsonl`、`~/.gateguard`、ecc-homunculus の observations などを介して、hook、観察 agent、`instinct-cli.py`、`/evolve` がつながる。
- **`ECC_*` 環境変数**：多数あり、1 か所の一覧には集約されていない。
- **名前規約**：言語別の command、agent、skill、rules を `<lang>-*` の命名だけで対応づけている。

## Claude Code が理解し、作業できるか

常時ロードされるのは skill / agent / command の名前と説明、および `paths` の無い rules だけで、本文は呼び出し時に読まれる。Claude Code の公式仕様では、skill 一覧の予算はコンテキスト窓の 1% で、超過すると呼び出し頻度の低い skill から説明が削られる。command は skill に統合されるため一覧に加わり、subagent の説明合計が 15,000 token を超えると起動時に警告が出る ([Skills docs](https://code.claude.com/docs/en/skills), [Sub-agents docs](https://code.claude.com/docs/en/sub-agents))。

| 観点 | agent-skills | ECC |
|---|---|---|
| 種別 | markdown 手順書集（実行コードは検証用のみ） | 環境構築システム（Node / Shell / Python / Rust） |
| 規模 | 208 ファイル、SKILL.md 計 7,494 行 | 約 4,200 ファイル、npm 2,615 ファイル / 17.7 MB |
| skill | 25（固定構造、上限 500 行） | 293（100〜900 行、形式は不揃い） |
| agent | 4（name / description のみ） | 68（tools / model 指定あり） |
| command | 9（Claude 用 .md、他に toml 複製が計 27 ファイル） | 94（legacy shim 扱い、description のみ） |
| hook | 4 スクリプト、自動登録なし（手貼り） | 24 個、プラグインが自動登録、profile で制御 |
| installer | なし（`/plugin` のみ、settings 非改変） | あり（settings.json への書き込み、`includeCoAuthoredBy: false` の既定書き込み、install-state、uninstall） |
| 依存の宣言 | なし（本文の名前参照、linter が dangling を警告） | manifests は module 単位で明示、command・agent・skill 間は暗黙 |
| 常時ロード（概算） | 約 2.5〜3k token | minimal 約 17k、developer 約 23k、full 約 37k |
| skill 本文（呼び出し時） | 平均約 3.4k、最大約 5.4k token | 全 293 本で約 669k token（全部は読まれない） |
| 整合性の担保 | skill-lint、command 3 コピーの parity、版数同期、routing eval（rank1 95% 以上）、実プラグイン導入の CI | `npm test` に validate-agents / commands / rules / skills / hooks など約 10 種と catalog / registry の drift 検査、coverage 閾値 |
| 編集用ガイド | CLAUDE.md 4.1 KB、AGENTS.md 5.4 KB、`skills/**` 限定の rule | CLAUDE.md 82 行、AGENTS.md 221 行、SKILL-DEVELOPMENT-GUIDE 920 行 |
| 既知のコード起因の問題 | 個別導入で checklist リンクが切れる、agent の tools 未指定 | 版数ずれ（2.2.2 未公開）、tarball の欠落ファイル、export-pdf.sh の traversal |

agent-skills は、各 skill が自己完結で、検証コマンドが単純（plain な `node scripts/validate-skills.js` など）、変更時の同期先も 3 種（command の 3 コピー、版数、reference リンク）に限られる。SKILL.md 計約 340 KB を一度には読めないが、1 skill ずつ読めば足りる。フィードバックの速さを重視して設計されている。常時 3k token は 200k 窓の約 1.5% で、説明文が削られる心配はほぼない。呼び出し時の負荷はむしろ大きく、`/spec` から `/review` まで通すと 4〜6 skill、15〜25k token を消費する見込みである（サイズからの推定）。auto-compaction 後の再添付は 1 skill 5,000 token までなので、最大級の skill（約 5.4k token）は末尾が切れる。

ECC は「読んで理解する」には大きすぎ、registry と CI に頼って触る規模である。安全に skill を足すには、SKILL.md、module のパス一覧への追記、catalog / registry の再生成、`validate-skills` の通過が要るが、これらは CI の失敗で気づく形で、CLAUDE.md には書かれていない（920 行のガイドが別にある）。hook を変えると sidecar とハッシュの更新も要り、`gateguard-fact-force.js`（1,960 行）や `install-lifecycle.js`（2,549 行）は全文を読まないと安全に触れない。常時ロードは full で skill 説明が約 94,000 文字あり、1% 予算をおよそ一桁超えると見込まれる（予算の単位が文字かトークンか公式に明記がなく、換算は仮定）。minimal でも agent 68 と command 94 の説明は常に載る。ECC 自身も profile を絞る前提で、`--skills` による skill 単位の選択、`--target claude-project`、`/context-budget` を用意している。実測ではなく計画出力に基づく数値であり、routing 品質の低下も実験していない。

## 採用の実務的な指針

新しく足すなら、まず agent-skills の plugin を入れ、必要な skill から使うのが安全である。導入で `~/.claude` の設定が変わらず、常時コストが小さく、名前空間が分かれて既存設定と衝突しにくい。特に採用価値が高いのは、skill の固定構造と anti-rationalization 表、`interview-me` と `doubt-driven-development`（fresh-context の敵対的レビュー）、`constraint-driven-development`（`@ts-ignore` の追加、テストの skip・削除、閾値の引き下げなど、基準を弱める変更の検知）、そして 3 層の routing eval（trigger の TF-IDF 判定は決定的で CI 向き）である。自分の skill 群にも同じ lint と routing eval を移植する価値がある。`simplify-ignore` は異常終了時にソースへプレースホルダが残りうるため、必要性が明確でない限り導入しないほうがよい。

ECC は全体導入せず、部品単位で読むのが現実的である。読む価値が高いのは、`hook-consent` の能力列挙（installer が何をするかを実行前に見せる設計）、ID 単位の settings マージと install-state による uninstall、hooks の sidecar とハッシュによるドリフト検出、`config-protection`（linter 設定を弱める編集の阻止）の考え方である。GateGuard は全 Edit の初回を止める挙動で、heredoc 誤検知などの報告もあるため、導入するなら strict でなく限定的に試すべきである ([#3152](https://github.com/affaan-m/ECC/issues/3152))。一方、fail-closed の Bash dispatcher と、Stop 時の formatter による無断書き換えは、そのままでは採用しにくく、取り込むなら例外時は許可に倒す形へ直す必要がある。導入するなら、`minimal` profile（hook runtime なし）を `--dry-run` で確認し、`--target claude-project` か plugin scope で始めるのが、`~/.claude` への衝突が最も少ない。`includeCoAuthoredBy: false` が自動で書かれる点、commit / PR の Co-Authored-By を残したい場合は事前に設定しておくこと、2.2.2 が公開されるまでは pin を外すか `@2.2.1` を使うこと（未実行の推測）も押さえたい。

## Conclusion

両者の違いは規模ではなく設計思想にある。agent-skills は「設定に触れず、少数の skill を検証で磨く」、ECC は「環境全体を管理し、その整合を CI で保つ」であり、Claude Code にとって扱いやすいのは前者、能力の幅が広いのは後者である。依存の宣言がどちらも frontmatter に無い以上、実際の依存関係の把握は本文の名前参照と CI 検証に頼ることになる。取り込む価値が高いのは skill の内容よりも、両者が持つ検証の仕組み（lint、routing eval、drift 検査、consent 表示）であり、自分の harness に足すならまずここからである。

未検証事項として、実インストール、hook の実行、`/context` の実測、`npm test` と各 validator の現行 HEAD での通過確認、両 repo の全 skill 本文の読了、`npx skills add` の書き込み先、agent-skills の `agents/` が manifest 無宣言で自動読込されるか（AGENTS.md の記述のみ）は、いずれも行っていない。
